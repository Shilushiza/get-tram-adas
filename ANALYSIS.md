# Что сделано и насколько это покрывает задание ГЭТ

Сверка с презентацией «ИИ-разбор эпизодов работы системы помощи водителю трамвая» (5 этапов пайплайна).
Статусы: ✅ сделано, 🟡 частично, ❌ нет.

## Данные, на которых всё построено
- 15 поездок, 6 вагонов (0210, 3119, 3139, 7752, 7821, 7826), сентябрь–октябрь 2026, 510 тыс. точек телеметрии, ≈4 234 км.
- Найдено 13 357 эпизодов: 3 099 по препятствию, 2 597 по светофору, 345 экстренных торможений, 72 юза, 7 244 по ограничению скорости.
- Главная находка: в JSON поля срабатываний (`m_*_act`) почти всегда `No`. Реальные срабатывания записаны в парных CSV (`dangObjAct/RealAct`, `trafLightRealAct`, …), поэтому CSV и JSON склеиваются по времени (совпадение 100%, корреляция скорости 0.998).

## Сверх задания
- Загрузка своих данных с разбором в реальном времени (поток эпизодов по SSE).
- Видео бортовых камер во вкладке эпизода (3 ролика из материалов хакатона, без синхронизации: у них нет меток времени).
- Colab-ноутбук `notebooks/feature_engineering.ipynb`: EDA, 60+ признаков, прогноз «торможение по препятствию в ближайшие 10 с» с разбиением по вагонам. Результат честный: PR-AUC 0.07 против 0.026 у случайного (лифт ≈2.7), ROC-AUC 0.76. Как прогноз пока слабо, как разбор факторов полезно. Кластеризация эпизодов.
- Субагенты и библиотеки: дизайн (31 источник), UX (31 скилл, 5 курсов), видео, Colab.

## Известные слабые места
1. Важность эпизода считается грубо: «важно» получает любое торможение по препятствию (3 591 из 6 113), нужно пересчитать по падению скорости.
2. Время в CSV с точностью до секунды, шаг записи до 5–7 с: порядок событий внутри секунды не установлен.
3. Публичный адрес держится на ноутбуке (туннель), постоянного хостинга нет.
4. Видео для защиты не записано.
